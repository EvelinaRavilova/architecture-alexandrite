# Выбор и настройка мониторинга в системе

## Мотивация

Есть несколько проблем отсутствия мониторинга:
1. Долгий и сложный процесс поиска причины возникновения проблемы, поиск начинается уже после жалоб пользователей.
2. Медленная реакция на изменяющуюся нагрузку, что приводит, например, к медленно выполняющимся запросам.

Таким образом, можно предотвратить потерю клиентов благодаря раннему обнаружению проблем и повышению производительности и надежности. Более того, это принесет компании новые бизнес-инстайты и разгрузит разработчиков для более интересных задач.

## Выбор подхода к мониторингу

1. MES - метод "Четыре золотых сигнала", так как этот метод подходит системам, которые предоставляют API. Метод позволит отслеживать пользовательский трафик, а также контролировать загруженность системы при таких тяжелых операциях, как расчет стоимости.

2. Интернет-магазин - метод "RED", так как в системе важны показатели, влияющие на конечных пользователей, такие как длительность запросов, количество неудачных запросов.

3. CRM - метод "Четыре золотых сигнала", так как система содержит API и работает с конечными пользователями.

4. База данных и брокер сообщений - метод "RED", так как он эффективен для сервисов, которые управляются запросами, и метод "USE", так как производительность сервисов снижается при интенсивном использовании.

## Какие метрики отслеживать

1. MES ("Четыре золотых сигнала"):
  - Latency:
     - Response time (latency) - выявление медленных запросов, таких как загрузка списка заказов (ярлыки: url_path, http_method, environment, instance)
  - Traffic:
    - Number of requests (RPS) - анализ уровня активности пользователей системы, определение активных периодов работы (ярлыки: url_path, http_method, environment, instance)
    - Number of requests (RPS) per user - анализ уровня активности определенного пользователя системы (ярлыки: url_path, http_method, user_id, environment, instance)
    - Kb tranferred (received) - контроль объема поступающего трафика
    - Kb provided (sent) - определение потенциально неоптимизированных запросов
  - Errors:
    - Number of HTTP 200 - определение успешности расчетных механизмов (ярлыки: url_path, environment, instance)
    - Number of HTTP 500 - показатель, который сообщает, что что-то не так (ярлыки: url_path, environment, instance)
  - Saturation:
    - CPU % - контроль производительности
    - Memory Utilisation - контроль возникновения утечек памяти

2. Интернет-магазин (RED):
  - Rate:
    - Number of requests (RPS) - анализ уровня активности пользователей системы, определение активных периодов работы (ярлыки: url_path, http_method, environment, instance)
    - Number of requests (RPS) per user - анализ уровня активности определенного пользователя системы (ярлыки: url_path, http_method, user_id, environment, instance)
    - Number of simultanious sessions - анализ пиковых нагрузок (ярлыки: session_id, environment)
  - Errors:
    - Number of HTTP 200 - картина успешности запросов (ярлыки: url_path, environment, instance)
    - Number of HTTP 500 - показатель, который сообщает, что что-то не так (ярлыки: url_path, environment, instance)
  - Duration:
    - Response time (latency) - выявление медленных запросов (ярлыки: url_path, http_method, environment, instance)
    - Cache hit - частота попадания в кэш (ярлыки: url_path, environment, instance)
  - CPU % - контроль производительности
  - Memory Utilisation - контроль возникновения утечек памяти

3. CRM ("Четыре золотых сигнала"):
  - Latency:
     - Response time (latency) - выявление медленных запросов (ярлыки: url_path, http_method, environment, instance)
  - Traffic:
    - Number of requests (RPS) - анализ уровня активности пользователей системы, определение активных периодов работы (ярлыки: url_path, http_method, environment, instance)
    - Number of requests (RPS) per user - анализ уровня активности определенного пользователя системы (ярлыки: url_path, http_method, user_id, environment, instance)
    - Kb tranferred (received) - контроль объема поступающего трафика
    - Kb provided (sent) - определение потенциально неоптимизированных запросов
  - Errors:
    - Number of HTTP 200 - определение успешности операций (ярлыки: url_path, environment, instance)
    - Number of HTTP 500 - показатель, который сообщает, что что-то не так (ярлыки: url_path, environment, instance)
  - Saturation:
    - CPU % - контроль производительности
    - Memory Utilisation - контроль возникновения утечек памяти

4. DB and RabbitMQ (RED + USE):
  - Rate:
    - Number of requests (RPS) - анализ нагрузки на сервис с точки зрения активности работы пользователей
  - Errors:
    - Transaction rollback count - количество неуспешных транзакций в БД для понимания огрехов в системе
  - Duration:
    - Query execution time - время выполнения запроса в БД, которое потенциально может расти со временем
    - Message delivery time - время доставки сообщений очереди, которое позволяет выявить, является ли очередь узким местом в производительности
  - Utilization:
    - CPU % - контроль производительности сервисов
    - Memory Utilisation for shop db instance - контроль загруженности БД
    - Memory Utilisation for MES db instance - контроль возникновения утечек памяти
    - Size of S3 storage - контроль переполнения хранилища для предотвращения падения сервиса
    - Size of shop db instance - контроль переполнения базы данных для предотвращения падения сервиса
    - Size of MES db instance - контроль переполнения базы данных для предотвращения падения сервиса
  - Saturation:
    - Number of dead-letter-exchange letters in RabbitMQ - определение ограничений очереди
    - Number of message in flight in RabbitMQ - определение "подвисания" сообщений как потенциальной проблемы потери заказов

## План действий

- Определить, какие данные собирать для мониторинга;
- Развернуть Prometheus для хранения метрик (можно использовать time-series базу данных);
- Развернуть Grafana для метрик и создать дашборды с панелями, определив пороговые значения метрик;
- Настроить оповещения с помощью встроенного раздела Alerts в инструменте.
